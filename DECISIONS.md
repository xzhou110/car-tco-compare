## ADR-001 — Command surface and CI gate: `npm run lint`, `npm run typecheck`, `npm run check`, and both deploy paths wait for `check` (2026-10-21)
- **Decision:** Adopt the shared engineering standard's command surface and gate (principles 6 and 8 in `D:/Meaningful/AI/agent-skills/rules/engineering-principles.md`) for the app in `app/`: ESLint in `app/eslint.config.js`, copied from the `engineering-audit` skill's template and adapted to this app's aliases (engine = `src/lib/`, ui = `src/components/`, no adapters folder yet, `src/state/` is the hook layer above the engine, the shell is `src/App.tsx` + `src/main.tsx`, `src/data/` ignored) with `@supabase/*` added to the engine's forbidden I/O imports; the scripts `"typecheck": "tsc --noEmit"` (new; `build` already type-checked), `"lint": "eslint ."` and `"check": "npm run lint && npm run typecheck && npm test && npm run build"`; a `check` job in `.github/workflows/deploy.yml` that the `build` job needs; the same `check` job in `.github/workflows/refresh-listings.yml`, which `refresh-and-deploy` needs, because that annual workflow is the repository's second deploy path and the standard says nothing ships red; and `.github/workflows/check.yml`, the same job for every other branch and pull request. "Validated" for an app change now means `npm run check` is green, locally and in Actions. The `rav4-alert/` scripts keep their own `package.json` and are outside this gate.
- **Context:** The 2026-10-21 fleet audit found a linter in one project, no project whose CI ran its tests, `check` with three meanings, and this app's `lib/listings.ts` calling the network from the pure folder. This app had `test` and `build`, no `typecheck`, `lint` or `check`, and two deploy workflows that only built. Retrofit steps 1 and 2 of the standard; the same change landed in car-shopping (ADR-010 there) and apartment-shopping (ADR-012 there).
- **What the lint found:** no errors outside three known debts, each marked by a one-line `eslint-disable` at the top of the file that names this entry (the standard's mechanism for an existing offender; the rules themselves stay at `error` for every other file): (1) `src/lib/listings.ts` calls `fetch` (`no-restricted-globals`); (2) `src/lib/supabaseClient.ts` creates a network client (`no-restricted-imports`, `@supabase/*`); (3) `src/state/useComparison.ts` types untrusted saved data as `any` in its hydration path, five times (`@typescript-eslint/no-explicit-any`). No file is over the 500-line lint cap. The boundary rules were proven with two throwaway files: six deliberate violations (React, Supabase and upward imports plus `localStorage` and `fetch` in `src/lib/`, a shell import in `src/components/`) were all reported, and the files were deleted. A clean lint with no warnings proves each marker is in use (ESLint warns on an unused directive).
- **Alternatives:** (a) Move the `fetch` and the Supabase client to an adapters folder now — rejected for this round: that is retrofit step 3 (purity), touches the callers (`App.tsx`, `AlertsModal.tsx`, `ConfirmPage.tsx`, `UnsubscribePage.tsx`) and is its own small session with the dependency check first. (b) Replace the `any`s with `unknown` now — rejected: the hydration functions spread and index the raw object, so the honest fix is one sanitizer at the edge, a change in behavior on malformed saves that deserves its own tests. (c) Set those rules to `warn` repository-wide — rejected: a marker on the offending file keeps every other file strict and makes the debt visible where it sits. (d) Leave `refresh-listings.yml` without the gate — rejected: it deploys. It was validated by parsing and structure only (jobs, `needs`, steps), not by a run: a manual run spends about 100 to 130 Auto.dev calls of the free 1,000 a month, so the first real run is the next manual or annual refresh.
- **Node:** CI stays on Node 22, as all three workflows already used (ESLint 10 needs ^22.13.0, which `node-version: '22'` resolves to); the machine runs Node 24 and `check` passes on both. Pinning one version (`engines` plus the workflows) is open. The `check` step receives the same two public repository variables as the deploy build so the gate builds exactly what deploys; nothing in lint, typecheck or the tests reads them.
- **Debt recorded (open, in `PROJECT.md`):** the three markers above (steps 3 and the sanitizer); pre-existing and unchanged, one app file over the 300-line reading limit (`src/components/AlertsModal.tsx` 337), to split at its next touch (retrofit step 4); `prototype/js/app.js` (432 lines) is the no-build reference outside `app/` and outside the lint.
- **Local gate (added later the same day):** a root `package.json` forwards `dev`, `test`, `lint`, `typecheck`, `build` and `check` to `app/` (`npm --prefix app run <script>`), so the root answers the standard's command surface (principle 6) and the machine's global pre-push hook, which runs `npm run check` after the secret scan wherever the root `package.json` defines it, gates every push (principle 8; `rules/machine-windows.md`). It gates the app only; the `rav4-alert/` scripts stay outside. A red check blocks the push; `SKIP_CHECK=1` skips the gate once and is never the way to push red code.
- **Reversible?** Yes — remove the four devDependencies (`eslint`, `@eslint/js`, `typescript-eslint`, `globals`), the three scripts, `eslint.config.js`, the three marker comments, the two `check` jobs, `check.yml` and the root `package.json`.

## ADR-002 — Deal Alerts logs name subscribers by id, failures turn the run red, the model-year bound follows the calendar (2026-10-22)
- **Decision:** (1) The scripts `alerts.yml` runs never print a subscriber's address: `alert-cron.mjs` and `send-confirmations.mjs` name a subscriber by the first 8 characters of their id (a UUID), the `out/` inspection files are `cron_<id8>.html` / `.xlsx`, and a provider error is logged as message text only with the address replaced by `<subscriber>` and any other address (for example the account owner's, which Resend's testing-mode error names) by `<email>` (a short local helper in each script). (2) Each subscriber runs inside its own try/catch; a watchlists query error, a Resend send error, and a failed write of the "already sent" record (`sent_state` in the digest, `confirmation_sent_at` in the confirmations) each count as a failure; after the loop the script prints `<n> of <m> subscriber(s) failed` and sets `process.exitCode = 1`. `cache-refresh.mjs` sets it when `expire_stale_listings` fails. `alerts.yml` keeps `continue-on-error` on the refresh and confirmation steps (ids `refresh`, `confirm`) so digests still go out, and a last step fails the run when either step's `outcome` is `failure`. (3) The Auto.dev year range ends at `MAX_MODEL_YEAR` (calendar year + 1, exported once from `rav4-alert/config.mjs`, which has no import-time side effects) instead of a fixed 2026.
- **Context:** The repository is public, so its Actions logs are readable by anyone, and they printed every subscriber's address. A watchlists error read as "no watchlists", a Resend error only logged, and the two `continue-on-error` steps hid their failures behind a green run. In October 2026 the 2027 model year is already on sale and the annual snapshot rebuild runs January 1.
- **Alternatives:** a hash of the address as the label — rejected: the id is already random and non-identifying, and the owner can look it up in Supabase. Counting only send errors — rejected for the record writes: the mail went out, but tomorrow's digest repeats its NEW badges or the confirmation is mailed again, which the owner should see. One shared logging module — rejected for now: two short copies are smaller than a new file both scripts import.
- **Next model year:** both TCO engines (`app/src/lib/tco.ts`, `rav4-alert/tco.mjs`) already clamp age at 0, so a car one model year ahead costs the same as this year's; `app/src/lib/tco.test.ts` now locks that in. The app's year dropdown is built from the snapshot, and its year inputs have no upper bound.
- **A run that stays red:** an address Resend always rejects (a 422) fails every day, because nothing is recorded for it. When the same id fails day after day, look it up in Supabase `subscribers` and set `unsubscribed_at` (or delete the row).
- **Reversible?** Yes: restore `${MIN_YEAR}-2026`, drop the helpers and the try/catch, and remove the last workflow step and the two ids.
